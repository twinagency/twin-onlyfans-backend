playback, assigned agency access and conversation handover ownership.

## Production verification

The database backup was verified with pg_restore before migration. Both running
processes passed explicit schema checks after migration. The API and worker share
the same writable persistent spool; the API retains read-only access to the image cache.
ffprobe is available in the worker image.

Actual authenticated requests verified the agency namespace/version handshake,
an empty account result for an unassigned synthetic scope and read-only write refusal.
The existing creator binding, connection and outgoing-policy snapshot were unchanged.
At the backend swap, both enabled-runtime and enabled-delivery-policy counts remained zero.
The database, private sign-in browser and unrelated bot containers retained their IDs.

The API uses the Docker database address while the worker uses its existing host-network
database address. The release helper compares each connection with its own running
configuration and preserves both exactly.

## Operation and recovery

The one-off helper is `deploy/media-agency-release-20261020.py`. Its explicit phases are
backup, prepare, deploy, verify, enable and disable. Upload admission is held off for the
backend swap. The enable phase follows paired dashboard verification and updates
`/var/backups/twin-media-agency-20261020/verified.json` with the actual admission state.

Private backups and baseline settings remain on the original server under
`/var/backups/twin-media-agency-20261020`. The active native compose configuration is
`/etc/twin-onlyfans/media-agency-release-compose.json`. No credentials were added to source.

After schema 0088, retain the new compatible runtime if uploads need to be disabled.
Do not downgrade the database, delete recovery records/spool contents, or replay uncertain jobs.
The old 0087 runtime deliberately refuses an 0088 schema.
